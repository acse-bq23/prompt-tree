# Prompt Tree

开始先问「这次最多跑几层树？根节点算第 1 层。」用户已给出层数时直接沿用。1 层只测基线。说明预算量级，例如 3 层且每个父节点最多有 3 个方向时，上限为 13 个版本、26 次切分评测，原路径对照和锁版前复测另计；例如 7 个入围版本各复测 5 次，还需 35 次完整 Validation。方向数取决于各节点自己的错误证据。

读取[首次接入](references/intake.md)确定业务控制点、样例、评分、授权预算和停止条件。在 project.prompt_entry 记录实际用于评测的入口。入口由业务源码抽取或多文件合成时，用 project.prompt_sources 列出原文件。项目已有独立批处理基线时，用 project.baseline_accuracy_report 指向该次完整准确率报告，核对其模式、Prompt 和数据版本。把用户确认的正整数层数写入 task.max_layers，按照[配置合同](references/contracts.md)填写两份配置。仅在用户授权时使用 mock。

## 按轮提交，比较当前与历史分支

以下 `<cli>` 指本 Skill 的 scripts/prompttree.cjs，要求 Node.js 22+。

```sh
node <cli> prepare --project project.json --task task.json --run RUN
node <cli> layer-submit --run RUN --plan level-1.json --wait
```

第 1 层计划为 `{"level":1,"nodes":[{}]}`。默认使用 **--wait**：工作进程在后台运行整层，等待端在结束时交回一次结构化回执。通过宿主的异步命令/完成通知等待；保持本次任务活跃，收到回执后同一任务自动继续。一次把整层交给执行器，无需逐样例或逐候选查询进度。

1. 生成下一轮候选前，沿每个父节点的 parent_event_id 回溯到根，读取各代实际 Prompt 改动、假设及授权的 Search 结果。按同一 case_id 串起各代预测，找出持续错误、首次退步、曾经修复又复发的题，以及新改动要保住的正确行为。对同一机制，检查前面各层其他分支已经试过的改法和结果，再决定沿用、收窄或换方向。具体记录方式见[跨层生成提案](references/layers.md#跨层生成提案)。Validation 仅查看聚合指标。
2. 提交下一轮前，在层计划旁保存父节点复盘，按[错因拆分与分支取舍](references/layers.md#错因拆分与分支取舍)记录每个父节点发现了哪些机制、各自的证据，以及哪些值得分开实测。不同机制各派生一个兄弟候选；同一条提示语中两个可以独立起效的约束也要拆开。只有单一方向成立时可以只展开一个，写明其余错例的去向。
3. 每条边只在直接父版本上做一处最小修改，引用该父自己的 Search 失败及已确认规则。每轮通过 layer-submit --wait 提交。还有可检验方向但本轮未选的父节点写入 defer，记录保住了哪些正确行为及剩余错因；确定结束用 stops。
4. 每轮把当前分支与历史最佳 Validation 汇总分、暂缓节点一起比较。连续两轮未刷新最佳时复查暂缓池；出现证据更明确的旧方向也可以提前回访。有预算且两边都有独立假设时，同轮给当前分支和历史分支各一次机会。回访从历史父版分叉，以它自己的 Search 失败构造新提案。详见[历史分支回访](references/layers.md#历史分支回访)。达到深度或约定停止条件时，先做下文的结案复盘。

### 每条边的改动幅度

生成候选时先考虑替换、精简或复用已有规则。以直接父版本为基准，单次改动优先控制在 5% 以内，5% 到 10% 时复查是否可以再缩短。超过 10% 时先尝试缩写或把独立假设拆开；对于很短的 Prompt 或确有必要的大改，在提案中说明原因。这是软目标。检查累计净增长，避免连续几层重复追加同义规则或把个别工单写进指令。

提交前可对两份已渲染的消息模板运行 `node lib/edit-size.cjs 父版本.json 候选.json`（从技能目录执行）。对包含角色标记和换行的完整文本按 Unicode 字符计数，去掉共同前后缀，取剩余新增和删除字符数中的较大值，除以父版字符数。等长替换也计入改动；净增字符另算。长手册会稀释百分比，还应检查新增字符的绝对量和独立样本的回归。

## 停止与交付

锁定前按预定规则找出暂定入选版，核查它实际测过哪些子版。将全部 Search 样本按 ID 对齐到基线、该版、子版和相关旁支，检查已修复、持续错误与回归。对浅层入选版尤其要问：未测方向能解释哪些父版错例，要保住哪些正确行为？记录值得补测的最小改动或足以停下的具体原因。尚有深度、授权预算和新证据时，从该版补测后再比较全部完成版本；必要时在剩余预算内继续检验其后代。收益持平、证据不足或预算用尽时允许浅层版本胜出。对有随机性的模型，树停止生长后先按下节复测，再按冻结的实质提升门槛和档内规则锁版。独立测试在锁版后开启。

```sh
node <cli> finalize --run .prompttree/runs/R-001 --version VERSION_ID --reason plateau
```

深度上限只约束单条分支。若已评的顶层版本全部落后于全树最佳验证分，回执进入 review_whole_tree。用 tree-review 盘点每个版本，包括已展开、暂缓、已停止的旧节点。先找低分分支相对领先版答对了哪些题，再看能否用直接父版自己的错例修回其副作用。对照子版已测方向，同一父版避免重复试相同改法。有证据则回访对应父版，顶层可提供参考证据。普通收尾需要保存本轮逐节点决定，详见[全树复盘](references/layers.md#全树复盘)。顶层并列或独占最佳时可按深度结案。其他可选停止理由由 `--help` 和 [执行合同](references/contracts.md) 指明。输出 `summary.md`、中文 `report.html`、英文 `report.en.html`、完整 Prompt、版本来路与评测。先读 manifest 与摘要，再审阅树、差异和失败依据。Probe 先导出验证锁版结果。项目完成独立测试后可附上回执，正式发布结论由项目另行给出。

### 锁版前复测

探索时每版先测一次。接入时把入围标准、重复次数、预算、同档门槛和最终同分顺序写入 plan.md。通常取验证领先的若干版本，纳入截断位置的全部并列者和有比较价值的原领先版。全树复盘结束后冻结候选快照和顺序。对于有随机性的模型，默认每个入围版新增五次完整 Validation，筛选成绩单列。

每轮交错运行所有候选，保持题目、分组、Prompt、模型配置与评分器一致。每个候选每轮使用独立请求标识和空响应缓存，并从实际发送与完成回执核对全部批次。独立新请求也可能返回相同答案。发生中断只恢复同一试验，重复回执只计一次。预算不足或有缺轮时明确给出覆盖范围，补齐前保留暂定结论。

### 差多少值得换版

新实验在首次复测前把 `selection_policy` 写入冻结计划。先根据业务成本定义值得换版的最小提升。缺少业务标定时，准确率可先用 **1.0 个百分点**的绝对差作为工作起点，在每轮 360 题上相当于平均 3.6 题。其他主指标按自身量纲和业务代价设置。该门槛是实际选版偏好；均值、波动范围和逐轮胜负仍分别报告。

1. 比较所有入围版与**最高验证均值**的差距。相差小于门槛或完全相等的版本进入最高档，差距达到门槛即分档。始终以最高分为参照，避免相邻节点串联扩大范围。
2. 对有拒识行为的任务，提前声明拒识输出标签。在最高档内比较误拒率，即本应受理却输出拒识标签的次数除以全部本应受理的次数。以档内最低误拒率为参照，建议用 **0.5 个百分点**作为起始门槛，保留误拒差距小于门槛或完全相等的版本。缺少拒识业务的项目跳过此步；已启用误拒比较而证据缺失时补齐回执。
3. 在余下版本中选**渲染后 Prompt 字符最少**的一版，长度相同按冻结名单顺序。报告列出均值领先版、最高档名单、误拒率、长度及实际入选版。只用 Validation 作上述决定。独立测试可验证这些版本在另一批样本上的表现。

用 `retest-summary` 汇总、`finalize --retest` 核对并归档同一份决定。历史计划沿用其冻结的规则。事后演算单独标识，供下次实验预设门槛时参考。[配置及回执格式](references/contracts.md#锁版前复测回执)

### 在树上展示锁版后的独立测试

项目完成测试后运行 `node <cli> report-test --run RUN --plan test/report-plan.json`。计划包含当前 `experiment`、主指标 `metric`、完整轮数 `rounds`、测试集路径 `dataset` 和回执索引路径数组 `indexes`。路径相对计划所在目录；索引的 `receipts` 每项给出 `version_id`、从 1 起的 `round` 和相对该目录的 `result`。原测和补测可分别使用一个索引。每次导入列全要展示的版本。

在树顶结论和 Prompt 对比表旁直接解释两种评测。验证复测用同一批验证题观察模型的轮间波动，依据多轮均值和预设规则选版。独立测试在锁版后使用优化和选版阶段留出的另一批题，检验效果能否延续；其结论单独记录。

报告按实际版本显示单次验证初筛、锁版前验证均值、锁版后测试均值和各自轮数。绿色锁版标记来自冻结的验证决定。蓝色测试行展示项目回执的结果。节点保留汇总预览，点击可展开逐轮成绩；右侧「评测」并列列出验证与独立测试的每轮得分、分子和分母、轮均值及范围。树顶用同一测试集对照锁定版与其他已测版本中均值最高的一版，沿用验证时约定的实质提升门槛解释是否同档。任意两版的 Prompt 对比也逐轮并列呈现两个阶段，分别按右版减左版报告均值差，并用冻结门槛判断这一对版本的差距。全树锁版仍以验证均值最高版为参照。缺少门槛时仅报告差距。

报告格式要求：离线 `report.html` 的页首须在 Prompt Tree 名称旁显示项目 Logo（`assets/prompt-tree-mark.png`）。导出时将 PNG 内嵌到 HTML，使报告可作为单文件离线打开。

默认生成交付文件，应用到原项目需要用户要求。报告与评测的案例导出由任务证据策略控制，默认不分享业务原文。

## 中断与继续

```sh
node <cli> status --run .prompttree/runs/R-001
node <cli> layer-resume --run .prompttree/runs/R-001 --level 2 --wait
```

从合同和事件记录恢复，检查在途、未知运行、实际预算与版本。读取 [恢复与限制](references/recovery.md) 处理缺失结果、超时、文件变化或完整性错误。

本 Skill 提供工作方法，持续执行由宿主提供。只有用户明确要求创建宿主持久目标时才使用该能力，可参考 `assets/long-task.md`；普通任务也可以使用同一目录跨会话继续。实验报告完整交付与 Prompt 是否改善分别判断。
