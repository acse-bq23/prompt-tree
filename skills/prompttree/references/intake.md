# 首次接入一个业务仓库

在业务仓库根目录工作，把本次接入的计划、适配器、数据快照及两份配置放在新的 `.prompttree/intake/<name>/`。已存在已确认的接入时，检查源文件、评分和数据是否仍适用，复用适用部分。实验目录由 prepare 单独创建。

## 选一个可测的控制点

运行 `node <skill>/scripts/prompttree.cjs discover --workspace .`。Git 仓库列出已跟踪及未忽略的文件，无 Git 时使用 ripgrep。输出是文件名、可能的用途和模型调用行号。生成代码、动态注册、私有样例目录或其他语言可能需要沿业务入口手工追踪。

从一次真实请求反查模型调用、消息构造、原生 Prompt、模板变量，以及后处理。对候选位置各记一行「源文件和符号 → 哪些调用使用它 → 测试/缺陷/样例依据 → 可观察的业务结果」。从现有缺陷、已知失败或测试覆盖的业务风险出发，优先选有可重放输入、可判定预期和独立修改位置的一处。只有推测时写明待基线验证。若缺陷来自解析器或数据，记录证据并回看其他控制点。

## 从样例设计评测

1. 盘点 fixtures、历史回归、输入/期望输出对、测试断言和业务规范。标出每条标签的来源、适用范围和难例。只有输入的样例可用于重放；要计入业务分数，还需可验证的期望或已确认的判定规则。
2. 保留已有且独立的 Search/Validation 切分；正式 Test 留存。若只有一个样例池，转换为 JSON 数组或 JSONL，加稳定的 case_id。按工单、会话或同源输入分组，去重并核对覆盖。已看过并据此设计修改的失败例留在 Search。未拆分且未参与调优的池可执行：
   ```sh
   node <skill>/scripts/prompttree.cjs split --dataset cases.jsonl --group ticket_id --out .prompttree/intake/R1/splits
   ```
   命令按组键哈希排序，约七成组进入 Search，两边至少各一组，返回可填入 task.datasets 的路径与数量。样例确实相互独立时可以按 case_id 分组。一个独立组无法支持留出验证，只请求缺少的独立样例。分配好后只从 Search 看错误详情。
3. 优先复用评分函数；已有样例但没有评测器时，根据已确认的断言编写最小适配器，调用项目实际执行路径并计量模型调用，用项目标准完成比对。记录分子、分母、业务主指标、回归条件及选择/停止规则。至少用一个应通过和一个应失败的输出检查评分器，并确认改变候选会传到实际消息。接入改变了执行路径时配置 original_evaluate_argv，比对原路径和适配基准。在现有授权内向宿主提供诊断时，令执行器的 cases 只包含脱敏失败 ID 和错误类型，设置 task.evidence.search_cases_visible 为 true；导出的案例证据单独控制。执行器字段见 [合同](contracts.md)。
4. 在接入目录的 plan.md 记录选点证据、可编辑字段、样例出处、分组/数量、评分及规则来源、模型配置引用、预算和停止条件。样例不足时说明可评价的范围。分清仓库已有标准、用户已确认标准和仍待决定的标准。

## 只向用户询问需要决策的事项

例如：样例覆盖了多标签工单，规范却只定义单标签。给一个脱敏的 Search 例子，问「多个标签部分命中时，按整单全对还是逐标签计分？」并说明选择会改变哪个指标。一次合并影响这次实验的问题；可从代码找到的路径、参数和样例由 Codex 填写。已有授权预算可沿用；首次付费运行缺少上限时给出按样例数、候选数和单例上界推算的预算请求。

等待回答期间可完成无调用的适配与评分自检。业务标准有缺口时，在回答写入 plan.md 与 task.rules 后再 prepare。规则已有权威依据且执行已获授权时直接继续。黄金答案、切分与预算在 prepare 前冻结。技术前提确实缺失时说明具体缺项和已完成的接入工作。

## 确认后继续到报告

按 SKILL.md 提交根层并等待两个切分的基准结果，用 Search 的失败 ID 驱动最小修改。为独立假设从同一父节点派生兄弟；只有新修改依赖上一条时从该子节点继续。整层提交，工作进程为每个节点及切分生成稳定的 request-id。按事先固定的业务标准和回归条件比较，持平优先保留较小改动或基线。若基线已满足目标或没有可归因失败，直接交付只有根节点的树。返回报告路径、最佳版本、验证指标、调用量和数据局限。
